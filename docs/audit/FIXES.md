## Notes

- SEC-03-001 follow-up (`aefa027`): the saved passphrase only answers ssh's own `Enter passphrase for …` prompt. A later automated review asked for a stronger guarantee (ssh version check, or answering at most once). Not done: it rests on OpenSSH prefixing server keyboard-interactive prompts with `(user@host) `, which has not been tested against a real `ssh`.
- SEC-11-001: a `session.json` written by an earlier version may still hold secrets until the next save rewrites it (the app saves on startup once the session has loaded; `SessionStore` also sanitizes on read).
- Verified, not fixed (needs a decision): BUG-06-001 / BUG-11-001. `disconnectStorage` has no caller in the renderer, so SFTP children, askpass servers and per-session agents live until the app quits or the profile is saved; and `StorageRegistry.getOrCreate` returns an existing provider and ignores the new config, so a password typed after a failed first attempt is ignored unless it is saved to the profile (saving disconnects). A fix needs reference counting across tabs and window moves, and evicting a provider whose first connection failed.
- Still unverified: UI findings in files 10-13 (BUG-10-001/002/005, BUG-12-001, BUG-13-001..005) and BUG-02-003 onwards at lower severities.
- BUG-03-002, agent lifetime: a per-session smartcard/FIDO2 agent is registered under the profile id (`smartcardSessionAgents.set(config.id, …)`) and only torn down when a terminal with that id exits (or the app quits). A second concurrent connection with the same profile id overwrites the entry, so the first agent process is no longer tracked; a tunnel never triggers the teardown at all. This affects two terminal tabs of one profile equally, so it is a design limit of the per-profile key rather than a tunnel bug. A fix needs per-connection ids (the UI matches tunnels to profiles through `connectionId: config.id`, so that id cannot simply change) or reference counting. Left open.
- BUG-04-003 changes a deliberate behaviour (the doc comment on `mergeRecords` described layering remote over local so local-only fields survive). Those fields are still kept; only fields the payload does carry now follow the remote. K8s profiles already worked this way (`replaceKeepingContext`).
- The queue in BUG-04-005 means a hung provider call now blocks later sync operations instead of running beside it.

## Follow-up check of `replaceKeepingLocalOnly` (BUG-04-003), after release 0.96.69

Read against the profile types and the push path (everything except the excluded fields is pushed, so the merge sees every other field).

- **Regression found and fixed: `lastUsedAt`.** It records when a *device* last opened a profile, but travels in the payload like any field. Before BUG-04-003 a newer remote record without it left the local value alone; with "remote replaces local" it was cleared, so this device lost its entry in the recent connections after any remote edit. The merge now keeps the later of the local and remote value (`laterTimestamp`). Test: `tests/main/ProfileSyncService.test.ts` (fails without the fix). **Not in 0.96.69**; needs the next release.
- **Known trade-off, not fixable here: version skew.** "The remote record replaces the local one" cannot tell a field that was cleared on another device from a field an *older app version* does not know about. Profile saving has no allow-list (`PROFILES_SAVE_SSH` stores the object as sent), so an older version only drops a newer field if its own edit form rebuilds the object field by field; that cannot be checked from this code base (it holds one version). If two app versions are used side by side, a profile edited on the older one can clear a newer-version-only field on the newer one at the next pull. A schema/version marker in the sync payload would be needed to do better.

## Tests for `DirectorySyncService.apply()` (coverage follow-up) and a second look at SEC-09-002

`apply()` can copy over and delete files, and had almost no tests (the file was at 53.8 % line coverage). 20 tests added in `tests/main/DirectorySyncService.test.ts`; the file is now at about 91 % lines / 86 % branches. They cover: the sync root is created first (and an existing one is fine), folders are created shallowest first before files go into them, new and changed files are copied from the source entry path to `target/relativePath` (with `jobId`, `totalBytes`, progress callback), the source modification time is kept on the target (a failure or a missing time is not a failed copy), a failed copy or folder is recorded and the rest carries on, nothing is deleted unless `deleteExtraneous` is set, deletion goes deepest first and tells folders from files, a failed delete is recorded, and only the entries it is given are touched. Four deliberate mutations of `apply()` (reversed delete order, no mtime, delete without the flag, reversed folder order) are each caught.

**SEC-09-002 re-checked, still dismissed, now with a test.** The worry was a path leaving the target through `relativePath`. For entries the app builds itself it cannot: `buildTree` keys every entry by the last path segment of the name the provider returned and skips `.` and `..`, so a hostile SFTP server listing `../../evil.txt` ends up as `evil.txt` (test: *buildTree with names chosen by a hostile server*). What remains is unchanged: `apply()` trusts the `relativePath` of entries that arrive directly over IPC, and `joinPaths` for a local target is `path.join`, which would leave the target directory for a `..` segment. Only a compromised renderer can send such entries, and it can already call the storage IPC directly. Not asserted by a test, so that behaviour is not cemented; a check in `apply()` would be the defence in depth if wanted (see the decision below).

## Session restore after SEC-11-001 (found by running the app)

SEC-11-001 stopped file manager tabs from writing their secrets to `session.json`, which is right, but a tab restored after a restart then had no password, passphrase or secret key. Run in the real app with a saved SFTP profile (password) and a saved S3 profile:

- **SFTP tab after a restart:** a dialog *"Password Required for SFTP — Profile … has no saved password"*, although the profile has one. Before the fix to SEC-11-001 the tab connected by itself, from the session file.
- **S3 tab after a restart:** it connected with no secret key (`secretAccessKey` is taken straight from the tab's config). Not shown against a real S3 server; the inference rests on the session file and `S3StorageProvider.ts`, so a real server would be expected to reject it.

**Fix:** `lib/savedSecrets.ts` (`withSavedSshSecrets`, `withSavedS3Secrets`) fills in what a restored tab lacks from the saved profile, matched by profile id, only the fields that are missing (password, passphrase, S3 secret key, session token, proxy password; never a PIN), and not from a deleted profile or one whose authentication type has changed. `DualPaneExplorer` applies it where a restored tab connects by itself. Secrets stay out of the session file. 6 unit tests (`tests/renderer/savedSecrets.test.ts`); re-run in the app: after a restart the SFTP tab shows no dialog and connects straight away, as before the restart. The S3 half was covered by the unit tests only when this was written; afterwards it was run by hand against real servers (`npm run dev:prod`, i.e. a build with the fix): an SFTP profile and an S3 profile, both with a saved password / secret key, reconnected by themselves after a restart. That says nothing about the released `0.96.69`, which was only seen failing in the test profile (SFTP dialog), not with a real S3 server. This is in the working tree after `0.96.69`; the released `0.96.69` still has the problem. <!-- pragma: allowlist secret -->

### Follow-up: the restored secrets must not follow an edited target (automated security review of `d3ee1f3`)

The first version of `savedSecrets.ts` matched a restored tab to its profile by id alone. The session file is not protected against being edited, and since the fix to SEC-11-001 it no longer holds the secrets itself, so editing a tab's `host` to another server and restarting would have made the app fill in the profile's password and connect there. The secrets are now only filled in when the tab still names the same target as the profile: for SSH the host, the port (a missing port is 22) and the user; for S3 the endpoint, the region and the access key; for a proxy password the proxy's host and port (the rest of the profile's secrets still follow when only the proxy differs). A tab opened by the app itself always matches, so normal restores are unaffected. Tests for each mismatch (they fail without the change). Not done: rebuilding the whole connection from the saved profile and taking only view state (paths) from the session, which would be stricter but is a larger change.

### Decision on `apply()` trusting its entries: left as it is

Correction to the note above: an absolute `relativePath` does **not** escape the target (`joinPaths` strips leading slashes for remote targets and `path.join` puts it under the target for local ones); only `..` segments do. And `relativePath` is not the only thing `apply()` trusts from the renderer: a delete uses the entry's own `targetEntry.path`, and a copy reads from `sourceEntry.path`. A real guard would rebuild every path from `relativePath` and check that it stays under the root (or check the entry paths against it), for both copying and deleting, with tests for both. Decided not to do it: the entries come from the renderer, which can already call the storage IPC with any path, so `apply()` gives it no new capability; the guard would only protect against a bug in the renderer. Paths the app builds itself cannot leave the tree (`buildTree`, tested).
